Why LangGraph?

The pieces underneath create_agent

Where we are

Since Week 2 we have written agents like this:

agent = create_agent(model=model, tools=TOOLS,
                     system_prompt=SYSTEM_PROMPT,
                     checkpointer=InMemorySaver())

One call gives us the whole loop: the model proposes a tool call, the runtime executes it, the result goes back, and round it goes until the model answers in words.

We have used that loop. We have not yet been able to change it.

Four things we cannot ask it for

  • Check the model’s proposed tool call before it runs, and refuse some of them
  • Branch on something other than a tool call — the customer’s tier, the length of the conversation
  • Run two lookups at once and combine the results
  • Stop, wait for a person to approve something, and pick up where we left off

None of these is exotic; each is ordinary in an application people actually use. And none of them is a parameter of create_agent.

The same library, one level down

create_agent is not a different technology. It builds a LangGraph graph and runs it, and that graph is available to us directly.

Three elements, and only three:

  • State — the data the graph carries
  • Nodes — functions that read state and return an update
  • Edges — what runs next

We’ll take each one in turn, and then put them together.

State: one dict, shared

State is a dictionary, described with a TypedDict so the keys are declared:

class SupportState(TypedDict):
    message: str
    reply: str

Every node receives the whole state. No node receives arguments of its own, and there are no globals — if a node needs something, it must be in the state.

Nodes return updates, not state

A node returns only the keys it changed:

def billing(state: SupportState) -> dict:
    return {"reply": "Billing team: we will review the charge."}

It never touches message, so it does not mention it. LangGraph merges the update into the state for us.

Note what a node is: a plain function. No decorator, no base class. Anything you can write in Python can be a node.

How updates combine

By default a key is overwritten — the last write wins:

def n1(s): return {"items": ["a"]}
def n2(s): return {"items": ["b"]}
# after n1 then n2:  {"items": ["b"]}

For most keys that is what we want. For a conversation it is a disaster: each model reply would erase everything said before it.

Reducers

A reducer is a rule attached to a key saying how an update combines with what is there:

class MessagesState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

add_messages appends rather than replaces. MessagesState is built in, and it is the state every agent we write from here on will use.

One detail worth knowing: if an incoming message carries the same id as one already in the list, add_messages replaces it instead of appending. That is how a message gets edited in place.

Edges: the fixed kind

builder.add_edge("write_joke", "improve_joke")

The route was decided when we drew the edge. Whatever the state says, improve_joke runs next.

A graph of only fixed edges is a workflow: the model does the writing, but it makes no decisions about what happens next.

Edges: the conditional kind

A conditional edge hands the decision to a function:

def route(state: SupportState) -> Literal["billing", "general"]:
    text = state["message"].lower()
    if any(w in text for w in ["refund", "charge", "payment"]):
        return "billing"
    return "general"

builder.add_conditional_edges(START, route)

The function reads the state and names the node to run next. Now the path is chosen while the graph runs, not while we write it.

That annotation is doing work

def route(state) -> Literal["billing", "general"]:

LangGraph reads the return type to learn which nodes this edge can reach. That is how it draws the branches.

Replace it with -> str and the router still works perfectly — while the diagram quietly collapses to a single arrow from start to end. The code is right and the picture is a lie.

The alternative is to pass the destinations explicitly:

builder.add_conditional_edges(START, route,
                              {"billing_query": "billing",
                               "general_query": "general"})

Use that form when the string the function returns is not a node name.

START and END

builder.add_edge(START, "router")
builder.add_edge("billing", END)

Two markers, not functions of ours. START is where the input enters, END is where the graph stops. A node with no path to END runs forever.

Compile, then run

graph = builder.compile()
graph.invoke({"message": "I want a refund"})

compile() checks the graph — unreachable nodes, edges to names that do not exist — and returns something runnable. It is also the moment a checkpointer is attached.

invoke returns the final state. stream gives it to us step by step, which is how we watch a graph make its decisions:

for chunk in graph.stream(state, stream_mode="values"):
    print(chunk)

A router is still not an agent

Our router decides once, on the way in, and then the work runs to completion.

An agent decides, acts, looks at what came back, and decides again. That is a cycle — the graph returns to a node it has already visited, and the model’s tool calls are the routing signal.

Cycles are the reason this is a graph library and not a chain library. We build one in the next notebook.

When to use which

create_agent is not deprecated by any of this. For a straightforward tool-using agent it is the right call, and it is less code to get wrong.

Reach for the graph when you need what it cannot give you: a check between the model and a tool, branching on something other than a tool call, parallel work, or a pause for human approval.

Knowing the graph also means that when create_agent misbehaves, we know what it is doing.

In summary

  • State is a shared dict; nodes return only what they changed
  • Reducers decide how updates combine — appending for messages, overwriting for everything else
  • Fixed edges make a workflow; conditional edges make a decision
  • Cycles are what turn a workflow into an agent
